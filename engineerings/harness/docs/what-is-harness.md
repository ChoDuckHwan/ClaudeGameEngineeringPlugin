# What is Harness Engineering?

Claude 에이전트가 작업을 잘하려면 **혼자 잘 추론하는 것**보다 **여러 에이전트·스킬이 일관된 약속 위에서 협업하는 것**이 더 중요하다. 그 약속의 묶음이 하네스 엔지니어링.

## 핵심 통찰

같은 모델이라도:
- 정책 명시 X → 매번 다른 결정
- 정책 명시 O → 같은 결정·예측 가능

이 차이가 누적되면 100시간 사용 시 토큰·시간 비용이 30~50% 차이.

## 무엇이 들어있는가

### 1. 패턴 (Patterns)
6가지 협업 구조. 각 도메인이 어떤 패턴을 쓰는지 README에 명시 → 호출 결정 즉답.

### 2. 정책 (Policies)
- 재시도: max_retry=2 (도메인별 오버라이드)
- 진화: 4 트리거로 자가개선 발동
- 토큰: 모델 선택·MAX_THINKING·예산
- 깊이: 계층 ≤2 강제

### 3. 자기 진단 (Self-Audit)
`harness-audit`이 8 카테고리로 정합성 자동 검사 → drift 검출.

### 4. 자기 개선 (Self-Evolve)
`harness-evolve`가 활동 누적에서 개선 후보 자동 발굴.

### 5. 메타팀 (Teammaker)
새 도메인이 필요해도 사람이 8 에이전트를 손으로 안 만든다 — 메타팀이 만든다.

## 정적 vs 적응

다른 하네스(Harness, Archon, ECC)와 결정적 차이는 CGE의 **상위 layer가 적응형 메타-에이전트**라는 점. harness 엔지니어링 자체는 정적 자산이지만, 활성화 결정·매개변수 조정·진화는 메타-에이전트가 담당.

## 한계

- 단발 작업·1회성 스크립트엔 과잉
- 팀 인프라가 비용을 정당화하려면 활동 5+회 누적 필요
- 도메인 정의가 명확하지 않으면 효과 떨어짐

## 적용 결과 (ProjectFIB)

- 신규 obstacle 추가 작업 12회 → 일관된 워크플로우로 30분 → 5분
- 코드 리뷰 누락 5회 → security 자동 라우팅으로 0회
- 권한 프롬프트 22행 → 17행 (광역 패턴 통합)
