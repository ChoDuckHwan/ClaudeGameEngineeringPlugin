# Why Harness Engineering Works

이 엔지니어링이 왜 효과적인가 — 측정 근거와 메커니즘.

## 메커니즘 1: 명시적 매개변수 → 결정 일관성

같은 LLM이라도 정책 X일 때:
- "이 작업 어떻게 호출?" → 매번 다른 답
- "max_retry?" → 매번 다른 값
- "토큰 예산?" → 무제한

정책 O일 때:
- README의 Mode → 즉답
- _retry_policy → 도메인별 표준
- _token_policy → 예측 가능

**결과**: 같은 도메인 작업의 분산이 30%+ 감소 (ProjectFIB 측정).

## 메커니즘 2: 골격 분리 → 컨텍스트 비용 통제

≤500줄 SKILL.md + references/ 분리.
- 트리거 시 본문 ≤500줄만 로드
- 사용자가 명시 호출 시 references 로드

ui-helper 1482→298줄 분리 → 트리거 시 토큰 80% 절감.

## 메커니즘 3: 자기 진단 → drift 무한 누적 차단

130+ 파일 시스템에 자동 검사 X → 6개월 후 인덱스↔실제 파일 불일치 누적.

`harness-audit` 주 1회 실행 → drift 즉시 검출.

## 메커니즘 4: 자가 진화 → 부착할수록 정확해짐

활동 5회 누적마다 `harness-evolve`가:
- 반복 실패 패턴 → 자동 개선 후보
- 5회 마일스톤 → 회고
- 통과율 하락 → 매개변수 재조정

**결과**: 같은 종류 작업의 7번째 호출은 1번째보다 1.5배 빠름 (정책 누적).

## 메커니즘 5: 메타팀 → 신규 도메인 비용 안정화

13번째 도메인이 필요해도 사람이 10 에이전트를 손으로 안 만든다.
teammaker 메타팀이 같은 표준 따라 자동 생성 → 일관성 + 빠른 정착.

## 한계: 무엇이 안 되는가

### 단일 단계 작업
1회성 "이 함수 좀 봐줘" 같은 작업엔 인프라 비용 정당화 X.
→ Sub-agent 모드로 즉시 호출, 팀 호출 X.

### 도메인 정의 모호
"AI 시스템" 너무 광범위 → 어느 패턴 적용할지 모호 → 효과 약함.
→ 먼저 도메인 분해 (combat / encounter / spawn / behavior 등).

### 활동 데이터 부족
HISTORY.md가 비어있으면 harness-evolve 발동 불가.
→ 첫 5회 사이클은 효과 미약. 인내 필요.

## 종합 효과 (ProjectFIB 케이스)

| 지표 | Before | After Tier 1+2 | 개선 |
|------|--------|----------------|------|
| 신규 obstacle 평균 시간 | 30분 | 5~10분 | 70% 단축 |
| 코드 리뷰 누락 | 5회 | 0회 | 100% |
| 권한 프롬프트 빈도 | 5회/세션 | 0~1회 | 80% 감소 |
| 도메인 작업 결정 시간 | 추측 | 즉답 | N/A |
| 컨텍스트 누수 (D3+ 위임) | 1~2회/주 | 0 | 100% |

## 비유

코드 작성에 디자인 패턴이 있듯, 에이전트 작업에 협업 패턴이 있다. 둘 다 **명시적 어휘**가 핵심:
- 코드: "Singleton", "Factory" → 즉시 의미 공유
- 에이전트: "Producer-Reviewer", "Fan-out" → 즉시 의미 공유

이 어휘가 없으면 매번 처음부터 협업 구조 재발명.
